# 내부 툴·B2B·운영 업무

> 근거: toss.tech 디자인 아티클 143편(2026-11-21 수집)의 본문만 사용했다. 출처는 규칙마다 글 제목과 URL로 달았다. 「」 안은 원문 그대로다. 색·크기·간격·모션 값 같은 시각 스펙은 `visual-style.md`에 있다.

## 이 파일을 읽을 때
- 상담·심사·정산·권한 관리 같은 운영 어드민, 사내 업무 툴, 슬랙봇처럼 동료(상담원·계약팀·운영자·디자이너·개발자)가 사용자인 제품을 설계하거나 고칠 때 읽는다.
- 사장님용 장부·포스·결제 단말기, 광고주·보험설계사용 B2B 제품처럼 업무 현장에서 쓰이는 제품을 다룰 때 읽는다.
- 반복 수작업을 자동화할지, 흩어진 요청과 기능을 공통 규칙·패턴·플랫폼으로 묶을지, 매일 쓰는 업무 도구를 어떤 속도로 바꿀지 판단할 때 읽는다.

## 핵심 요약
- 업무용 툴은 동료가 많은 일을 정확하고 빠르게 하도록 돕는 제품이고, 내부 사용자의 업무 속도는 최종 고객의 경험까지 바꾼다 (§1.1, §1.2)
- 설계 전에 사용자가 어떤 순서와 방식으로 일하는지 현장에서 관찰하고, 가능하면 그 업무를 직접 해 본다 (§2.1, §4.1)
- 기존 업무 흐름에서 꼭 남길 단계만 추리고, 제품이 이미 아는 정보와 반복 입력은 제품이 대신 채운다 (§3.1, §3.2)
- 문제가 너무 많아 보이면 하나의 원인으로 압축하고, 업무 방식을 먼저 통일한 뒤 자동화한다 (§4.1, §4.5)
- 제각각 보이는 요청·계약·기능에서 반복 패턴을 찾아 공통 규칙·시스템·플랫폼으로 만든다 (§5.1, §5.3, §5.5)
- 매일 쓰는 업무 도구는 익숙한 습관을 살리고, 작게 쪼개 배포하며, 큰 변화는 미리 여러 번 알린다 (§6.1, §6.3, §6.4)
- 업무용 툴의 성과는 작업 시간처럼 측정할 수 있는 지표로 개선 전후를 비교한다 (§6.8)
- 사용자가 이미 일하는 곳(메신저, 업무 화면) 안에서 일이 끝나게 하고, 복잡한 설정은 웹으로 뺀다 (§8.1, §8.4, §4.4)

## 1. 동료를 사용자로 보는 관점

### 1.1 업무용 툴은 동료가 정확하고 빠르게 일하도록 돕는 제품이다
**규칙**: 업무용 툴은 팀원과 고객이 업무시간 동안 많은 일을 정확하고 빠르고 효율적으로 하도록 돕는 것을 목표로 한다. 반복되는 일을 자동화하거나 더 효율적인 워크플로우를 줘서 사용자가 더 중요한 일에 집중하게 만든다.
- 왜: 토스 최초의 Product Designer(Tools)가 이 직무의 역할과 보람을 이렇게 정의했다.
- 근거: 「토스 팀원이나 저희 고객들이 업무시간 동안 많은 일을 정확하고 빠르게, 효율적으로 할 수 있도록 돕는 역할이지요.」 / 「반복되는 일을 자동화하거나 더 효율적인 워크플로우를 제공해서 사용자가 더 중요한 일에 집중하도록 만드는 것이 이 직무로 일하면서 얻는 보람이에요.」
- 출처: [토스 최초의 Product Designer(Tools)의 일하는 방식](https://toss.tech/article/1st-product-designer-tools)

### 1.2 내부 사용자의 업무 속도는 최종 고객의 경험으로 이어진다
**규칙**: 상담원·계약팀이 쓰는 툴을 최종 고객 경험의 일부로 보고 개선한다. 내부 툴의 비효율은 고객의 대기 시간, 만족도, 사업을 시작하는 시점으로 그대로 옮겨 간다.
- 왜: 토스뱅크에서는 상담원 툴이 원래 중요한 고려 대상이 아니었지만, 상담 속도가 빠를수록 상담 NPS와 하루 응답할 수 있는 상담 수(응답률)가 오르므로 카드 배송조회 업무의 비효율을 당장 풀 문제로 봤다. 개선 뒤 상담원의 업무 속도는 상담 NPS에도 좋은 영향을 줬다. 토스페이먼츠에서는 계약팀 심사 효율화가 사장님의 계약 경험 만족도(9.5점)로 이어졌고(§4.1), 계약팀이 사업자 번호·상호명 같은 정보를 한눈에 검토하는 툴 덕분에 입점 심사를 하루 안에 끝내 사장님이 더 빨리 판매를 시작할 수 있게 됐다.
- 근거: 「상담 속도가 빠를수록 고객 만족도(NPS)가 높아질 뿐 아니라 다음 상담에 빨리 응답하여 대기 시간을 줄이고 궁극적으로 하루동안 받을 수 있는 상담 수, 즉 응답률이 높아져요.」 / 「툴즈 디자이너로서 내부 제품의 유저인 상담원 뿐만 아니라 토스뱅크 유저의 경험까지 챙길 수 있어 뿌듯했던 경험이에요.」 / 「보이지 않는 부분에서도 이런 일들이 필요해요 그래야 하루라도 더 빠르게 사업을 시작할 수 있으니까요」
- 출처: [레거시 제품을 버리고 CS 효율 높이기](https://toss.tech/article/rebuild-legacy-cs-products), [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394), [당연했던 것을 새롭게 만드는 법](https://toss.tech/article/27346)

### 1.3 어드민도 디자이너가 처음부터 참여한다
**규칙**: 백엔드만 있는 어드민 제품이라도 디자이너 없이 PM/PO와 엔지니어끼리 착수하는 편이 빠르다고 가정하지 않는다. 디자이너가 처음부터 들어가 사용자 이해도가 높은 상태로 설계하게 한다.
- 왜: 디자이너 없이 하면 빠를 것 같지만 실제로는 쉽게 갈 길을 돌아가게 됐다. 디자이너가 처음부터 참여한 제품은 불필요한 일을 줄이고, 고객에게 잘 닿으면서도 빨리 만들어졌다.
- 근거: 「디자이너 없이 하면 더 빨리 할거로 생각하는 의사결정인 거죠. 그런데 디자이너가 없으면 쉽게 갈 길을 더 돌아가게 되더라고요.」 / 「사용자에 대한 이해도가 높은 상태로 디자인을 하기 때문에 점점 불필요한 일을 줄이고 사용자들도 만족하는 제품을 내보냈고요.」
- 출처: [토스 최초의 Product Designer(Tools)의 일하는 방식](https://toss.tech/article/1st-product-designer-tools)

### 1.4 사례: 디자이너 1명, 엔지니어 10명인 업무용 툴 팀의 기초공사 (문제 → 해결)
- 문제: 2020년 토스 최초의 Product Designer(Tools)는 PC 환경용 디자인 시스템이 거의 없고, 디자이너 1명에 풀스택 엔지니어 10명이며, 디자인 QA까지 맡아 업무 시간이 모자랐다.
- 해결: 어떻게 일할지 정의하는 일을 먼저 했다. 플랫폼 디자이너와 함께 기존 PC 디자인 시스템 초안을 놓고 무엇을 자주 쓰는지, 컴포넌트별 최소 요구사항이 무엇인지 정의해 시스템에 적용하고 제품에 구현했다.
- 결과: 기초공사를 한 차례 끝내자 업무 효율이 늘었다. 효율을 높이려면 일을 가장 작은 단위로 쪼개 그것부터 점검하고 처리해야 한다는 것을 체감했다.
- 근거: 「그래서 어떻게 일할지를 정의하는 일을 먼저 했어요.」 / 「효율을 높이기 위해는 가장 작은 단위로 쪼개고 그것부터 점검하고 처리해야한다는 걸 적용해 본 시간이었어요.」
- 출처: [토스 최초의 Product Designer(Tools)의 일하는 방식](https://toss.tech/article/1st-product-designer-tools)

### 1.5 보이지 않는 내부까지 디자인한다
**규칙**: 겉으로 드러나는 화면뿐 아니라 보이지 않는 내부 업무와 내부 효율화 제품까지 같은 기준으로 치열하게 고민한다. B2B SaaS 디자인은 참고할 공식이나 환경이 부족하다는 점을 알고 시작한다.
- 왜: B2B와 내부 고객용 제품을 만드는 Product Designer(Tools) 챕터는 토스 서비스와 내부 효율화 제품 모두 이 철학의 결과물이라고 말한다. 또 B2B SaaS 디자이너는 업계 특성상 참고할 공식이 부족해 고민을 풀기 어려운 경우가 많아서, 이 챕터는 자신들의 경험이 그런 디자이너에게 실무 참고 자료가 되길 기대하며 디자인 컨퍼런스를 열었다.
- 근거: 「겉으로 드러나는 부분 뿐 아니라, 보이지 않는 내부까지도 치열하게 고민하며 디자인」 / 「B2B SaaS 제품을 만드는 디자이너들은 업계 특성 상 참고할 수 있는 공식이나 환경이 부족해 고민을 해결하기 어려운 경우가 많은데요.」
- 출처: [Simplicity24, 성공의 문을 여는 가장 평범한 질문](https://toss.tech/article/simplicity24)

### 1.6 사용자 수가 적은 내부 제품도 리소스 대비 임팩트로 판단한다
**규칙**: 내부 제품도 어떤 제품·인프라의 임팩트가 클지 팀이 치열하게 논의해 방향을 정한다. 사용자 수가 적다는 이유만으로 버리지 않고, 적은 리소스로 큰 임팩트를 낼 수 있으면 만든다.
- 왜: 콘텐츠 매니저 3명만 쓰는 에디터 개선에 반대했던 디자이너가 PO의 권유로 콘텐츠 발행 과정을 참관한 뒤 문제의 크기를 체감했다(§1.7). 개선한 제품의 효용이 사내에 퍼지자 디자이너·개발자가 없는 인사·CX 같은 팀도 글 게시에서 비슷한 어려움을 겪고 있었다는 것이 드러났고, 제품은 전 계열사로 확장됐다. (사용자 수가 적은 제품의 판단 기준 전반은 → decision-making.md)
- 근거: 「어떤 제품 혹은 인프라를 만들었을 때 임팩트가 클지, 어떤 일이 더 중요한지 팀원들간에 치열한 논의를 통해 방향을 정해요.」 / 「사용자 3명인 제품도, 만들어볼만 하지 않을까요?」
- 출처: [사용자 3명인 제품, 만들어야 할까?](https://toss.tech/article/only-3-users-product)

### 1.7 사례: 콘텐츠 매니저의 글 발행 과정 (Before → After)
- 상황: 콘텐츠 매니저 3명이 금융 콘텐츠를 쓰고 발행하던 사내 에디터. '최소 리소스, 최대 효율'을 목표로 기존 에디터 개선이나 오픈소스 기반 신규 개발 대신 노션을 쓰는 제3의 방법을 골랐다(후보 비교는 → decision-making.md, data-and-experiments.md).
- Before: 10여 개 툴을 오가며 HTML 문법으로 코딩하듯 글을 썼고, 글 하나를 발행할 때도 편집 어시스턴트와 여러 차례 커뮤니케이션해야 했다.
- After: 디자인 시스템과 노션 텍스트 블록을 1:1로 매칭해, 노션에 글을 쓰면 디자인 시스템이 적용된 서비스 화면이 자동으로 그려지게 했다. 어드민에서는 앱 안 노출 위치처럼 서비스와 만나는 접점만 설정한다.
- 왜 바꿨나: 글 쓰는 곳과 서비스에 올라가는 결과 사이의 간극을 없애 서식 편집을 따로 하지 않게 하려고. 작업 시간이 적게는 1/3, 많게는 1/10로 줄었고, 콘텐츠 매니저 혼자 편집·발행까지 하게 되어 더 좋은 글을 쓰는 데 집중하게 됐다.
- 근거: 「이 시스템과 노션의 텍스트 블록을 1:1로 매칭해주기만 하면, 노션에서 글 쓰는 것과 서비스에 글이 올라가는 것의 간극을 아예 없앨 수 있었어요.」 / 「작업 시간이 적게는 1/3, 많게는 1/10까지 줄었어요.」

## 2. 관찰로 시작한다: 업무의 순서와 패턴을 먼저 본다

### 2.1 설계 전에 사용자가 어떤 순서와 방식으로 일하는지 관찰한다
**규칙**: 업무용 제품은 사용자가 실제로 어떤 순서와 방식으로 일하는지 관찰한 뒤 설계를 시작한다. 인터뷰로 문의 유형과 업무 방식을 파악하고, 사용자가 남긴 업무 메모와 실제 작업 장면까지 빠짐없이 본다.
- 왜: 토스뱅크 상담 툴은 디자인 전에 카드 배송조회 문의 유형과 상담원의 업무 방식을 인터뷰로 파악해 핵심 문제 두 가지를 찾았다. 토스페이먼츠 계약 심사 툴은 디자이너가 일주일 정도 계약팀 사무실에 상주하며 직접 계약 업무를 해 보고, 일곱 명의 업무 관리 메모를 모두 살펴 자동화 지점을 찾았다(§4.1, §4.3). 상담 제품(토스원) 디자이너는 처음에 사용자를 본 적도 없이 개선하려 했던 것을 돌아본다(§2.4). 사장님 포스 사례처럼 사용자가 불편이 없다고 말해도 익숙해져 굳은 불편일 수 있다(현장 관찰 방법은 → research-methods.md).
- 근거: 「제품을 설계할 때 사용자가 어떤 순서와 방식으로 쓰는지 관찰한 뒤 시작해보세요」 / 「자동화 포인트를 찾아보기 위해서 계약 팀 일곱 명의 업무 관리 시스템 메모들을 빠짐없이 꼼꼼히 살펴봤는데요.」
- 출처: [레거시 제품을 버리고 CS 효율 높이기](https://toss.tech/article/rebuild-legacy-cs-products), [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394), [사장님에게 익숙한 불편함 깨부수기](https://toss.tech/article/27180)

### 2.2 사례: 상담원 어드민의 정보 구조 (Before → After)
- 상황: 토스뱅크 상담원이 카드 배송조회 같은 고객 문의를 처리하던 어드민. 상담원은 신규 어드민(헬프데스크)과 레거시 제품을 오가며 일했다.
- Before: 레거시 제품은 수많은 메뉴로 쪼개져 있어 필요한 화면을 찾기 어려웠고, 찾은 뒤에도 조회할 카드 정보를 반복 입력해야 했다.
- After: 고객이 보유한 상품을 먼저 찾도록 하이어라키를 수신·카드·대출로 나누고, 각 카테고리 안에서 어떤 계좌·카드·대출에 대한 문의인지 좁혀 가게 했다.
- 왜 바꿨나: 상담원은 고객의 대략적인 문의를 몇 가지 질문으로 점점 구체화한다. 가장 먼저 카드 종류와 번호를 물어 카드 하나를 특정한 뒤 정보를 조회하고 안내한다. 제품 구조를 이 대화 패턴에 맞췄다.
- 근거: 「고객과 상담원의 대화에서 패턴을 발견할 수 있었는데요, 고객의 대략적인 문의를 몇가지 질문을 통해 점점 구체화한다는 거에요.」 / 「따라서 고객이 보유한 상품을 먼저 찾도록 제품의 하이어라키를 설계했어요.」

### 2.3 문의 패턴과 대상의 상태에 맞춰 필요한 정보로 바로 보낸다
**규칙**: 사용자가 그 상황에서 가장 먼저 찾을 정보로 곧장 이동시킨다. 문의가 몰리는 패턴과 대상의 상태(예: 아직 쓰지 않은 카드)를 함께 보고 첫 화면을 정한다.
- 왜: 카드 배송 문의는 대부분 어제·오늘 막 신청한 카드에 관한 것이었다. 아직 사용 전인 카드라면 결제 내역은 묻지 않을 테니, 그런 카드를 누르면 내역 정보 탭이 아니라 배송 정보 탭으로 보냈다. 이런 구조 개선과 자동화(§3.2)로 카드 배송 상담 1건 처리 시간이 평균 94초에서 48초로 줄었고, 월 900여 건 기준 월 690분, 연 138시간을 아끼게 됐다.
- 근거: 「아직 사용 전이라면 배송 상황은 궁금해도 결제 내역에 관한 문의는 하지 않을테니까요.」 / 「월 900여 건의 상담이 이루어지는 것을 생각하면 월 690분의 시간, 연 138시간을 줄일 수 있게 되어요.」

### 2.4 사례: 상담 내용 입력창 (Before → After)
- 상황: CX팀원이 매일 쓰는 상담 제품(토스원)에서 상담 중과 상담 후에 자주 쓰는 상담 내용 입력창.
- Before: 사용자를 지켜보지 않고 만든 '뇌피셜 디자인' 시안. 상담 입력창을 새 창으로 띄워 한쪽에 늘 열어 두고 쓰게 하려 했다(결국 채택하지 않음).
- After: 상담 중인 고객정보 페이지 안에 매달린 플로팅 입력창으로 제공했다. 스크롤하면 따라다니고, 정보를 가리지 않도록 좌우로 옮기거나 언제든 접어 둘 수 있다.
- 왜 바꿨나: 관찰과 인터뷰를 해 보니 사용자는 많은 정보를 한눈에 보고 싶어 했고, 상담 후 메모를 옮겨 적었고, 스크롤로 위아래를 오갔다. 여러 창을 켜 두고 일해서 입력창이 정보 창 아래로 가려지면 찾기 어려워했다.
- 근거: 「빈도 높은 일, 그리고 많은 사용자들이 하시는 일인데 사실 처음에는 이걸 개선할 때 지켜보지 않고 이 사용자분들을 본 적도 없이 이런 식으로 제품을 개선하려고 했었어요.」 / 「게다가 그런 상황에서 여러 창을 켜놓고 이 일을 하시니까 정보를 보는 창 아래에 입력하는 창이 가려지면 되게 찾기 어려워 하셨거든요.」

### 2.5 사례: 상담 내용 입력칸의 순서 (Before → After)
- 상황: 같은 상담 제품에서 상담원이 고객 정보를 확인하며 상담 내용을 입력하는 화면.

- 왜 바꿨나: 관찰 전에는 디자이너도 몰랐던 비효율로, 직접 보고서야 발견했다.

## 3. 반복 수작업은 제품이 대신한다

### 3.1 꼭 남길 단계만 추리고 중복 입력을 자동화한다
**규칙**: 기존 업무 흐름에서 꼭 남겨야 하는 구간만 추리고, 사용자가 중복으로 입력하는 내용을 찾아 자동화한다. 완전 자동화가 아니어도 불필요한 단계를 하나 덜어내는 것부터 시작한다.
- 왜: 업무용 어드민에서 중복 입력을 자동화하면 업무 효율이 크게 늘어난다. 리서치 플랫폼팀은 작은 액션 하나를 자동화하면서, 만드는 사람에게는 사소한 작업도 그 일을 반복하던 팀원에게는 체감되는 변화라는 것을 확인했다(→ decision-making.md).
- 근거: 「기존 업무 흐름에서 꼭 남겨야 하는 구간만 추려보세요.」 / 「사용자가 중복으로 입력하는 내용이 있는지 확인해보세요. 자동화한다면 업무 효율이 제곱으로 늘어날 거예요.」
- 출처: [레거시 제품을 버리고 CS 효율 높이기](https://toss.tech/article/rebuild-legacy-cs-products), [업무 효율화, 작은 단계부터 다시 보기](https://toss.tech/article/research_process)

### 3.2 사례: 상담원이 배송업체에 문의를 전달하는 업무 (문제 → 해결)
- 문제: 상담원이 배송업체에 문의할 때 요청 유형별 템플릿에 맞춰 하나하나 입력했고, 전달 단계가 많아 복사·붙여넣기를 반복했다.
- 원인: 배송업체만 확인·처리할 수 있는 일인데 고객은 토스뱅크 고객센터로 문의하므로 전달이 필요했다. 접수 건이 쌓이는 곳이 없고 배송업체와의 연락 채널도 따로여서 전달 과정이 복잡해졌다.
- 해결: 전달 업무 자체는 없앨 수 없으므로 더 간편하고 빠르게 전달하도록 바꿨다. 메모장 템플릿에서 헬프데스크가 이미 알고 있어 사람이 입력하지 않아도 되는 항목을 지우고 바로 전달하게 했다.
- 결과: 직접 입력해야 하는 정보가 11개에서 2개로 줄었다.
- 근거: 「위와 같은 이유로 전달 업무 자체가 없어지는건 불가능해요.」 / 「메모장에 적어 전달하는 템플릿을 보고 헬프데스크가 이미 알고 있어 굳이 사람이 입력하지 않아도 되는 것을 제거해보니 직접 입력해야하는 정보가 11개에서 단 2개만 남게 되었어요.」
- 출처: [레거시 제품을 버리고 CS 효율 높이기](https://toss.tech/article/rebuild-legacy-cs-products)

### 3.3 사례: 인터뷰 일정을 캘린더에 만드는 운영 업무 (Before → After)
- 상황: 리서치 수요가 늘고 B2B 고객·외국인 등 섭외 대상이 다양해지자, 리서치 플랫폼팀이 속도를 지키려고 리서치 프로세스를 점검했다. 프로세스를 액션 단위로 쪼개 각 액션에 '이건 왜 필요하지?'를 묻고, 내 기준이 아니라 그 일에 영향받는 사람 기준으로 우선순위를 정했다. 참석자 자동 추가처럼 안 되는 부분은 내려놓고 가능한 부분부터 테스트 기간을 두고 적용했다.
- Before: 날짜·시간 설정, 주제 입력, 참석자 추가, 회의실·화상 링크 설정, 가이드·질문지 템플릿 첨부, 잘못 입력된 정보 확인을 매번 손으로 반복했다.
- After: 리서치 시트에 날짜와 시간만 입력하면 캘린더 초대, 가이드·질문지 템플릿 첨부, 기본 설정이 자동으로 만들어진다.
- 왜 바꿨나: 반복 입력과 검수 작업을 없애 휴먼에러와 확인 리소스를 줄이려고.
- 근거: 「리서치 시트에 날짜와 시간만 입력하면, 이 모든 과정이 자동으로 생성되도록 만들었어요.」 / 「반복 입력·검수 작업이 사라지고, 휴먼에러와 확인 리소스가 크게 줄었어요.」

### 3.4 사례: 고객에게 송금 내역 문서를 보내는 업무 (문제 → 해결)

### 3.5 사례: 사내 프로그램 권한 신청의 완료 알림과 처리 (Before → After)
- 상황: 팀원이 사내 프로그램 권한을 신청하고 관리자가 처리하는 과정. 인터널 프로덕트 디자이너가 이틀간 20명 넘는 팀원을 만나 '신청'과 '완료'만 남기고 나머지를 자동화·시스템화했다(신청 페이지와 입력 항목 개선은 → funnels-and-flows.md).

- 왜 바꿨나: 평소 가장 많이 쓰는 메신저로 메시지를 보내면 접근성이 올라간다고 판단했다.

### 3.6 사례: 관리자의 승인 버튼까지 없애기 (Before → After)

- Before: 버튼 클릭 한 번이라도 반복되면 관리자의 업무 흐름이 끊기고 업무시간을 관리에 써야 했다.

## 4. 업무 방식을 통일하고 제품이 일을 이끌게 한다: 계약 심사 툴 사례

### 4.1 사례: 늘어나는 PG 계약 신청을 감당하지 못한 심사 업무 (문제 → 해결)
- 문제: 사장님의 PG 계약 신청 경험은 쉬워졌지만 토스페이먼츠 내부 계약팀의 심사 경험은 그렇지 못해, 늘어나는 신청을 처리하기 벅찼다. 결국 사장님에게서 토스페이먼츠를 이용할 이유가 없다는 충고까지 받았다.
- 원인: 신청 건수가 느는 속도보다 이를 처리할 시스템을 갖추는 속도가 느렸다. 인터널 프로덕트 디자이너가 일주일 정도 계약팀 사무실에 상주하며 직접 계약 업무를 해 보니, 아주 많아 보이던 문제가 사람마다 업무 방식이 천차만별이라는 하나로 압축됐다.
- 해결: 지금 시스템을 조금 고치는 데 그치지 않고 시스템에 녹아든 비효율 자체를 뿌리 뽑기로 했다. 심사 방식 통일(§4.2), 업무 관리 자동화(§4.3, §4.4), 안내문 자동화(§4.6)를 했다. 사람은 꼭 해야 할 일만 하고 나머지는 제품이 하는 '똑똑한 비서' 같은 제품을 지향했다(→ principles.md). 문제가 너무 많고 복잡해 보일 때는 그 문제들을 풀어 이루려는 궁극적인 목적만 생각해 보라고 조언한다.
- 결과: 한 건당 약 40분 걸리던 심사 시간을 3분까지 줄였고, 계약 경험 만족도 점수는 9.5점이었다.
- 근거: 「사장님의 계약 신청 경험은 진짜 쉬워졌는데, 토스페이먼츠 내부 계약팀의 계약 심사경험은 그러지 못했거든요.」 / 「한 건당 한 40분씩 걸리던 심사 시간을 3분까지 단축을 했어요.」
- 출처: [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394)

### 4.2 사례: 계약 심사 화면 (Before → After)
- 상황: 계약팀이 PG 계약 심사를 진행하는 내부 제품 화면.
- Before: 심사 결과를 입력하는 기능만 있고 심사를 어떻게 진행하면 되는지 가이드가 전혀 없었다. 사람마다 심사 순서가 제각각이었고 확인할 내용을 놓치는 일이 잦았다.
- After: 확인해야 할 내용을 나열해 성격에 맞게 다섯 묶음으로 나누고, 단계별로 화면을 분리해 한 방향으로만 쭉 심사하면 끝나도록 설계했다.
- 왜 바꿨나: 개인의 숙련도에 따라 심사 결과가 달라지면 안 되므로, 초심자도 숙련자도 놓치는 부분 없이 심사하도록 제품이 가이드를 주려 했다.
- 근거: 「그래서 초심자도 숙련자도 아주 쉽게 놓치는 부분이 없이 심사를 진행할 수 있도록 제품에서 가이드를 잘 주고 싶었어요.」 / 「심사를 다섯 단계로 나누고 각 단계에서 확인해야 될 내용들을 담아서 화면을 분리했어요. 내용을 놓칠 일이 없게 한 방향으로만 쭉 심사하면 심사가 끝나도록 설계했어요.」
- 출처: [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394)

### 4.3 사례: 배정된 계약 업무 관리 (Before → After)
- 상황: 자동으로 배정된 계약 심사 업무를 담당자가 관리하는 방식.
- Before: 담당자가 배정받은 업무를 스프레드시트나 메모장에 옮겨 하나하나 입력하고 선택값을 바꿔 가며 각자 관리했다. 중단된 심사의 문제가 풀렸는지 사람이 계속 들락날락하며 확인했다.
- After: 심사를 시작할 수 있는 상태가 되면 '처리 전' 탭에 쌓이고, 모든 심사 프로세스가 끝나면 '처리 완료' 탭으로 옮겨진다. 제품이 알아서 업무를 관리한다.
- 왜 바꿨나: 계약팀 일곱 명의 업무 관리 메모를 보니 해야 할 일·기다리는 일·끝난 일로 나뉘었고, 그중 기다리는 일에서 많은 시간과 노력이 낭비되고 있었다.
- 근거: 「크게 해야할 일 기다리는 일 끝난 일 이런 식으로 나눠볼 수 있겠더라고요. 그런데 이 기다리는 일 여기서 많은 시간과 노력들이 낭비되고 있다는 걸 깨달았어요.」 / 「이게 심사를 시작할 수 있는 상태가 되면 처리 전 탭에 쌓이고요. 모든 심사 프로세스가 다 끝나면 처리 완료 탭으로 옮겨져요.」
- 출처: [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394)

### 4.4 사례: 심사 가능 상태를 담당자에게 알리는 방식 (Before → After)
- 상황: 사장님이 서류를 다시 올리는 등 심사를 이어 갈 수 있게 됐을 때 담당자에게 알리는 방식.
- Before: 알림을 슬랙으로 보내 담당자가 슬랙과 업무 화면을 오가야 했고, 불편한 것은 물론 누락이 생겼다.
- After: 업무 처리용 제품인 JIRA에서 힌트를 얻어 알림을 제품 안에 녹였다. 심사를 시작할 수 있는 상태가 되면 어떤 처리를 해야 하는지 적힌 티켓이 자동으로 만들어지고(예: 사장님에게 요청한 서류가 다시 올라오면 '서류확인 필요' 티켓), 담당자는 티켓을 하나씩 처리하며 하루 업무를 끝낸다.
- 왜 바꿨나: 해야 할 일을 찾아다니거나 놓치는 일을 없애려고, 알림과 처리를 업무 화면 한곳에 모았다. 사용자가 메신저에서 일하는 다른 사례에서는 메신저 안에서 처리하게 했다(§3.5, §8.1).
- 근거: 「슬랙과 업무 화면을 왔다갔다 하면서 보게 되니까 이게 불편한 건 둘째치고 누락되는 것들이 생겨나더라고요.」 / 「해야될 일감들이 티켓으로 만들어져있고, 그 티켓을 하나씩 처리하면서 하루 업무를 끝내도록 설계했어요.」
- 출처: [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394)

### 4.5 업무 방식을 먼저 통일하면 뒤따르는 자동화가 쉬워진다
**규칙**: 자동화보다 업무 방식 통일을 먼저 한다. 단계별 결과를 유형화할 수 있게 되면, 뒤따르는 기록 작업은 그 결과를 그대로 남기게 하기만 하면 된다.
- 왜: 계약 심사 방식을 다섯 단계로 통일하자 단계별 심사 결과를 유형화할 수 있었고, 심사 메모 자동화는 그 결과를 메모장에 그대로 남기게 하는 것으로 끝났다.
- 근거: 「첫 번째로 메모를 자동화하는 건 진짜 쉬웠어요. 앞에서 심사방식들을 다 통일했기 때문에 각 단계별로 나올 수 있는 심사 결과들을 좀 유형화할 수 있었는데요.」 / 「그거를 그대로 메모장에 남겨지게만 하면 됐어요.」
- 출처: [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394)

### 4.6 사례: 심사 결과를 사장님께 알리는 안내문 작성 (Before → After)
- 상황: 계약 심사 결과를 사장님에게 문자로 안내하는 업무. 디자이너에게도 미지의 영역이라 계약팀 사무실에 내려가 실제로 안내문을 쓰고 보내는 방식을 관찰했다.
- Before: 담당자가 개인 메모장에 통 텍스트 템플릿을 저장해 두고 복사·붙여넣기한 뒤 조금씩 고쳐 문자로 보냈다. 모든 경우의 수를 템플릿으로 만들어야 해서 관리가 어려웠다.
- After: 템플릿을 뜯어보고 공통 부분을 묶어 안내 문구를 조각으로 모듈화했다. 심사 결과에 따라 안내할 항목을 고르면 내용이 자동으로 채워진다.
- 왜 바꿨나: 통 텍스트 템플릿은 경우의 수마다 새로 만들어야 해 관리가 어려웠다. 바꾼 뒤 5분, 10분 걸리던 작성이 몇 초로 줄었고 안내 문구의 톤앤매너도 통일됐다. (문구 시스템 일반은 → ux-writing-errors-marketing.md)
- 근거: 「첫 번째 문제는 템플릿들이 통 텍스트로 있다 보니까 모든 경우의 수를 다 템플릿으로 만들어야 돼서 관리가 어렵다는 문제가 있었어요.」 / 「원래는 안내문 작성에 들이던 시간이 5분, 10분 정도 됐다면 이거를 몇 초 만에할 수 있게 시간을 많이 아낄 수 있었어요.」
- 출처: [100가지 문제를 한번에 해결하는 방법](https://toss.tech/article/27394)

## 5. 제각각인 요청에서 공통 규칙을 찾아 시스템과 플랫폼으로 만든다

### 5.1 사례: 제휴사마다 다른 정산 계약 (문제 → 해결)
- 문제: 제휴사와 돈을 주고받는 정산 업무에서 회사마다 수수료 계산 방식이 달라 비슷한 일을 매번 반복했고, 팀 인원이 많아도 일손이 모자랐다.
- 해결: 매번 다르게 하지 않고 공통 규칙을 찾았다. 비슷한 계약을 '구간별 수수료율'이라는 하나의 규칙으로 묶고, 복잡한 계약들을 표 하나로 정리해 매번 새로 디자인하지 않아도 되는 구조를 만들었다.
- 결과: 여러 회사의 정산을 같은 방식으로 처리하게 됐다. 규칙을 만들고 반년쯤 지나자 프론트엔드 개발자가 디자이너 없이 UI를 만들었다.
- 근거: 「이런 유사한 계약들을 묶어 ‘구간별 수수료율’이라는 하나의 규칙으로 정리했더니, 여러 회사의 정산을 모두 같은 방식으로 처리할 수 있게 됐어요.」 / 「이 시스템이 없었다면 지금도 저는 비슷한 화면 수백 장을 계속 만들고 있었을지도 몰라요.」
- 출처: [AI 시대에 디자이너로 살아남기](https://toss.tech/article/removing_designers_in_ai_era)

### 5.2 사례: 요구조건 문서를 쓰는 일까지 줄이기 (문제 → 해결)
- 문제: 정산 규칙을 만든 뒤에도 디자인 전에 요구조건 문서(스펙)를 쓰는 일이 남아 있었다.
- 해결: 정산 서비스를 요청하는 임직원이 몇 가지 설문에 답하면 그 정보로 UI가 자동 생성되는 매핑 시스템을 만들었다.
- 결과: 완전 자동화는 아니지만 어시스턴트 디자이너 혼자 작업할 수 있을 만큼 됐다. 앞서 개발자가 디자이너 없이 UI를 만든 일을 디자이너 없이 돌아가는 시스템의 신호로 봤다(AI 시대 디자이너의 역할 논의는 → ai-practices.md).
- 근거: 「정산 서비스를 요청하는 임직원이 몇 가지 설문에만 답하면 그 정보를 토대로 UI가 자동 생성되도록 매핑 시스템을 만들었죠.」 / 「완전히 자동화되진 않았지만, 어시스턴트 디자이너 혼자 작업할 수 있을 만큼은 되더라고요.」
- 출처: [AI 시대에 디자이너로 살아남기](https://toss.tech/article/removing_designers_in_ai_era)

### 5.3 사례: 상담 운영 제품의 60가지 비효율을 20가지 패턴으로 (문제 → 해결)
- 문제: 상담 업무 제품(비바매니저)은 오랜 시간 여러 사람이 규칙 없이 개발해 통일된 사용 경험을 주지 못했다. 처음에는 비효율마다 다른 문제라고 여겨 매번 새로 개선했다.
- 원인: 다 뜯어보기 전에는 수많은 백로그 중 어떤 경험이 반복되는지 알기 어렵다(→ problem-solving.md).
- 해결: 처음 몇 개월은 함께 봐야 하는 정보를 모으고, 다른 제품을 오가는 비용이 생기지 않도록 기능을 연결했다. 그러자 자동화할 것들이 보였다. 1년간 60가지가 넘는 운영 비효율을 하나씩 해결한 뒤, 비슷하게 반복되는 경험(정보 검색, 계정 차단·주문 취소 같은 처리, 특정 내역을 기관에 접수하고 진행 상태 관리, 데이터 수정·추가)과 여러 제품이 매번 새로 고민하던 것(로그인·본인 인증, 권한 관리, 메뉴 구조)을 묶어 규칙으로 만들고 20가지 정도의 패턴으로 시스템화했다.
- 결과: 비바매니저의 93%를 이 패턴으로 자동화하게 됐다.
- 근거: 「처음에는 다 다른 문제라고 생각해서 할 때마다 새로 개선했던 것들이 알고 보니 비슷한 경험이어서 하나의 해결책으로 통일될 수 있었던 거죠.」 / 「그 결과, 지금은 비바매니저라는 제품의 93%를 이 패턴으로 자동화할 수 있게 됐어요.」
- 출처: [잘 만든 시스템 하나로 미친 효율 얻는 방법](https://toss.tech/article/how-to-make-marvelous-productivity-with-well-made-system)

### 5.4 패턴 시스템은 만드는 사람과 쓰는 사람의 부담을 함께 줄인다
**규칙**: 패턴 시스템은 개발자가 기능을 하나하나 개발하지 않고 짧은 명령어로 추가할 수 있게 하고, 운영자가 기능마다 따로 배우지 않도록 사용 경험을 통일하는 것을 목표로 한다.
- 왜: 이렇게 만들자 CH 팀과 오퍼레이션 매니저가 기능마다 따로 학습하는 문제가 크게 줄었다. 특정 제품에서만 필요한 기능은 공통 규칙에서 빼고, 어떤 패턴부터 만들지는 일의 발생 빈도·건당 소요 시간·일하는 사람 수·휴먼 에러 리스크로 정한다(→ decision-making.md).
- 근거: 「개발자가 하나하나 힘들게 개발하지 않아도 되도록 짧은 명령어를 입력하는 것만으로 기능을 쉽게 추가할 수 있도록 구현했거든요.」 / 「그리고 무엇보다 익숙하고 일관되게 사용 경험이 통일되어 CH 팀이나 오퍼레이션 메니저 분들이 기능마다 따로 학습하는 문제가 훨씬 줄어들었어요.」
- 출처: [잘 만든 시스템 하나로 미친 효율 얻는 방법](https://toss.tech/article/how-to-make-marvelous-productivity-with-well-made-system)

### 5.5 사례: 계열사마다 같은 기능을 바닥부터 만들던 문제 (문제 → 해결)
- 문제: 조직이 커지며 필요한 기능은 느는데 만들 사람은 부족했다. 권한 관리나 착오송금처럼 모든 계열사에 필요한 기본 기능을, 제품이 새로 생길 때마다(송금 종류별로도) 바닥부터 따로 만들고 있었다. 또 인터널 제품을 두 개 이상 쓰며 일하는 경우가 절반 가까이 되는데, 제품마다 사용성이 달라 학습 비용이 높았다.
- 해결: 패턴 시스템을 다른 제품에도 적용하자는 제안에 인터널 플랫폼 팀이 공감해, 다른 팀 누구나 이 시스템을 쓸 수 있는 플랫폼을 만들었다.
- 결과: 시스템이 업데이트되면 플랫폼을 쓰는 모든 제품과 계열사가 혜택을 받는다. 망분리 환경에서도 쓸 수 있고, 플랫폼 자체 보안 장치 덕분에 제품마다 보안을 따로 고민하지 않아도 된다. 증권 원장 관리 시스템, 페이 어드민, AML 시스템 등이 이 플랫폼 위에서 만들어지고 있다.
- 근거: 「토스에서는 인터널 제품을 두 개 이상 사용해서 일하는 경우가 절반 가까이 되는데 아직도 제품들은 각기 사용성이 다르고 학습 비용이 높았거든요.」 / 「예를 들면 시스템이 업데이트되면 플랫폼을 사용하는 모든 제품과 계열사가 그 혜택을 누릴 수 있게 됐어요.」
- 출처: [잘 만든 시스템 하나로 미친 효율 얻는 방법](https://toss.tech/article/how-to-make-marvelous-productivity-with-well-made-system)

### 5.6 사례: 서로 다른 팀의 요청이 쌓이던 인터널 프로덕트 팀 (문제 → 해결)
- 문제: 토스의 모든 팀을 고객으로 하는 인터널 프로덕트 팀이 맥락이 다른 요청을 따로따로 진행하다 보니 제품 수가 크게 늘었고, 추가·변경 요청으로 제품별 운영 비용도 늘어 문제를 제대로 파 보기도, 요청을 그대로 반영하기도 버거워졌다.
- 해결: 요청을 하나씩 살펴보다가 완전히 다른 팀의 요청 사이에서 반복되는 패턴을 찾았다. 목적은 달라도 슬랙 메시지를 적절한 곳에 전달한다는 수단이 같았으므로 하나의 기능으로 묶고, 팀별 차이(특정 채널만, 멤버가 보낸 메시지만, 봇 메시지 제외 등)는 옵션으로 두었다(통합과 제품화 판단 기준은 → problem-solving.md, decision-making.md). 이 기능은 사용자가 직접 설정하는 오토메이션 제품으로 이어졌다(§8.8).
- 근거: 「그런데 이런 다양한 맥락의 문제들을 따로 따로 진행을 하다 보니까 그만큼 제품 수가 엄청 많아지는 거예요.」 / 「이거를 해결하려고 우선 각각의 요청들을 한 번 살펴보는 작업을 했어요. 그러다 보니까 이제 완전히 다른 팀에서 요청한 건데 반복되는 패턴들이 있는 것 같았어요.」
- 출처: [3,250개의 요구사항을 해결한 1개의 제품](https://toss.tech/article/27398)

### 5.7 사례: 그룹 권한 없이 설계했다가 서버 구조까지 갈아엎은 경험 (문제 → 해결)
- 문제: 초기 제품이라 단순하게 시작하려고 '그룹 권한' 기능 없이 설계했는데, 나중에 꼭 필요해지면서 서버 구조까지 갈아엎는 큰 비용을 치렀다.
- 원인: 토스 안의 더 고도화된 계정 체계를 알았다면 그룹 권한이 반드시 필요해질 것을 예측할 수 있었다. 내부 툴 디자이너는 계정 권한, 데이터 CRUD, 앱 미리보기처럼 처음 해 보는 구조나 흐름을 생각보다 자주 직접 정의해야 한다.
- 해결: 이런 러닝이 쌓이고 공유되도록, 작은 단위의 디자인 시스템을 넘어 챕터 전체가 중요한 의사결정과 노하우를 공유하는 'UX 시스템'을 목표로 삼았다.
- 근거: 「예전에 저는 ‘그룹 권한’ 기능 없이 제품을 설계했다가, 나중에 꼭 필요한 상황이 생기면서 서버 구조까지 갈아엎는 큰 비용을 치른 적이 있어요.」 / 「디자이너는 예상보다 자주, 처음 해보는 구조나 흐름을 직접 정의해야 하는 상황을 마주하게 돼요.」
- 출처: [AI 시대에 디자이너로 살아남기](https://toss.tech/article/removing_designers_in_ai_era)

## 6. 매일 쓰는 업무 도구를 바꾸고 효과를 확인한다

### 6.1 매일 쓰는 업무 도구는 작은 개선을 꾸준히 한다
**규칙**: 전문 사용자가 매일 쓰는 업무 도구는 한 번에 크게 고치기보다 작은 개선을 꾸준히 이어 간다. 변화의 크기 자체를 줄여 사용자가 당장 배울 것을 최소로 한다.
- 왜: 정보와 버튼 위치를 기억해 일하는 CX팀원은 제품이 바뀌면 바뀐 내용을 파악하느라 헤맸고, 그것이 고객 응대 지연과 상담 만족도 하락으로 이어졌다. 한꺼번에 고치려 해서 잘된 적은 한 번도 없었다. (변화의 크기를 줄이고 중요한 것부터 배포하는 판단은 → decision-making.md)
- 근거: 「근데 제품에 변화가 생기면 또 바뀐 내용을 파악하느라 헤매는 시간이 생기고, 그게 고객님께 응대하는데에 있어 지연이 되고 있으니까 상담 만족도가 조금 떨어졌던 것 같아요.」 / 「그래서 한꺼번에 고치려고 한 번에 하려고 해서 잘 된 적은 진짜 한 번도 없었어요.」
- 출처: [사용자의 공감 얻으면서 제품 뜯어고치기](https://toss.tech/article/27186)

### 6.2 익숙함을 편하게 느끼는 사용자라면 기존 사용성부터 파악한다
**규칙**: 사용자가 새것보다 익숙함을 더 편하게 느끼는 도구를 바꿀 때는, 기존의 편안함이 무엇이고 기존 사용성이 어떤지부터 파악해 포기하면 안 되는 습관을 가려낸다.
- 왜: 상담 제품 개편에서 기존 Ctrl + F 습관을 살린 검색은 사용법을 알려 주지 않아도 쓰였다(§6.3). 전문 사용자는 방어적이어서가 아니라 일에 몰입해야 해서 변화에 조심스러울 뿐이다(→ research-methods.md).
- 근거: 「그럴 때는 기존의 그 편안함이 뭔지, 기존 사용성이 어떤지 파악하는 것부터 시작하는 게 저는 도움이 되더라고요.」
- 출처: [사용자의 공감 얻으면서 제품 뜯어고치기](https://toss.tech/article/27186)

### 6.3 사례: Ctrl + F를 대체하는 상담 제품 검색 (Before → After)
- 상황: 한 페이지에 정보가 너무 많아 CX팀원이 수시로 Ctrl + F로 찾던 상담 제품. 데이터 로딩 속도 문제를 풀려면 당시 구조상 Ctrl + F를 막아야 해서, 팀은 속도를 택하고 대체 검색을 새로 만들었다(→ data-and-experiments.md, decision-making.md).
- Before: 기존 Ctrl + F는 필터링이 안 돼 키워드 하나에 40~50개 결과가 나와 한참 눌러 봐야 했고, 탭에 숨겨진 정보는 결과에 나오지 않았다.
- After: Ctrl + F 키로 검색창이 열리는 습관은 그대로 살렸다. 검색창을 열면 원하는 섹션으로 바로 가는 리스트를 보여 주고, 검색어를 넣으면 어디에 있는 어떤 정보인지 걸러서 보여 주며, 엔터로 다음 위치로 이동하는 동작은 유지하면서 숨겨진 정보까지 찾게 했다.
- 왜 바꿨나: 가장 빈도 높은 사용 목적(원하는 섹션으로 이동, 특정 정보 찾기)과 가장 익숙한 습관을 살리면서 기존 방식의 아쉬운 점만 보완했다. 그 결과 사용 방법을 알려 주지 않아도 자연스럽게 써서 학습 리소스가 들지 않았다.
- 근거: 「여기에서 사실 제일 중요하게 고민했던 건 기존 검색 경험에서 가져올 가장 익숙한 습관을 살리는 거였는데,」 / 「굳이 사용 방법을 알려주지 않으셔도 자연스럽게 사용을 했던 것 같아요. 그래서 학습하는 리소스가 들지 않다 보니까 그게 전 가장 좋았어요.」
- 출처: [사용자의 공감 얻으면서 제품 뜯어고치기](https://toss.tech/article/27186)

### 6.4 큰 변화는 미리, 여러 번 알리되 사소한 공지는 줄인다
**규칙**: 중요하고 큰 변화는 생각보다 훨씬 미리, 여러 번 반복해 공지한다. 사소한 공지가 너무 잦으면 피곤하므로 변화의 크기와 사용자 특성에 맞춰 융통성 있게 판단한다. 사용자가 제품과 만나는 순간까지 디자이너가 챙긴다.
- 왜: 기존 업무 흐름을 방해하지 않고 새 변화에 편하게 적응하게 하려면 변화를 전달하는 방식까지 설계해야 한다. (한 번에 많이 알리는 공지와 나눠 알리는 공지의 비교는 → ux-writing.md)
- 근거: 「그래서 중요하고 큰 변화는 생각보다 훨씬 미리 공지하고 여러 번 반복해서 공지를 하는 거예요.」 / 「근데 이제 또 너무 사소한 공지까지 너무 빈번하게 울리면 피곤할 수 있으니까 변화의 크기랑 사용자분들 특성에 맞게 고려해서 융통성 있게 판단하는 게 중요했던 것 같아요.」
- 출처: [사용자의 공감 얻으면서 제품 뜯어고치기](https://toss.tech/article/27186)

### 6.5 사례: 수십 가지 기능의 상담 제품 리빌딩 (문제 → 해결)
- 문제: 기존 상담 제품을 토스원으로 리빌딩해야 했고, 다시 만들어야 할 기능이 수십 가지가 넘었다.
- 해결: 첫 MVP는 고객 검색 화면과 결과 화면 두 개뿐이었다. 나머지는 반년에 걸쳐 우선순위가 높은 것부터 쪼개 배포했다. 리빌딩 전 환경도 섣불리 닫지 않고 새 버전과 예전 버전을 함께 운영하는 과도기를 두어 적응할 시간을 충분히 줬다.
- 근거: 「고객 검색하는 화면이랑 결과 보여주는 화면, 끝 아무 기능도 아무것도 없는」 / 「사실 진짜 리빌딩해야 되는 기능은 수십 가지가 넘었었거든요. 그런 것들이 반년에 걸쳐서 높은 우선 순위부터 쪼개서 배포를 했었어요.」
- 출처: [사용자의 공감 얻으면서 제품 뜯어고치기](https://toss.tech/article/27186)

### 6.6 레거시를 그대로 옮기지 말고 실제 업무 과정을 본뜬 제품으로 일원화한다
**규칙**: 사용자가 신규 제품과 레거시 제품을 오가며 낭비가 생기면 기능을 한 제품으로 일원화한다. 이때 레거시 화면을 그대로 옮기지 않고 실제 업무 과정을 본뜬 제품으로 새로 설계한다.
- 왜: 토스뱅크 상담원은 헬프데스크와 레거시 제품을 오가며 일했다. 팀은 레거시의 비효율을 청산하고 실제 상담 과정을 본뜬 제품을 만들기로 했고, 그 결과가 §2.2, §2.3, §3.2의 구조와 자동화다.
- 근거: 「상담사 분들이 2가지 제품을 오가며 생기는 낭비를 해결하려면 신규 제품인 헬프데스크로 기능을 일원화해야 한다고 판단했어요.」 / 「레거시 제품의 비효율을 청산하고, 실제 상담 과정을 본뜬 완전히 새로운 제품을 설계하자는 목표를 세운 거죠.」
- 출처: [레거시 제품을 버리고 CS 효율 높이기](https://toss.tech/article/rebuild-legacy-cs-products)

### 6.7 사례: 데이터 직군이 매일 쓰는 사내 툴 테이블센터 (문제 → 해결)
- 문제: 데이터 직군이 100명을 넘었는데 테이블센터는 데이터 엔지니어 한 명이 만든 초기 버전 그대로였다. 검색이 10초 넘게 걸려도 로딩 안내가 없었고, 원하는 결과가 안 나와 여러 번 검색해야 했다. 디자이너·서비스 개발자 없이 만들어져 구성과 위계가 복잡했고, 디자인 시스템을 쓰지 않아 일관성이 떨어졌다.
- 해결: 기존 서비스를 고치기보다 새 테이블센터를 만들기로 했다. 무엇부터 고칠지 모르는 상태였으므로 측정할 수 있는 성과 지표를 세워 나침반으로 삼았다(§6.8, → data-and-experiments.md).
- 결과: 검색 시간을 줄이는 개선(§6.9, §6.10)을 했고, 개선 전후 만족도 설문으로 전체 만족도가 오른 것을 확인했다.
- 근거: 「검색을 한 번 하면 10초 이상 걸리는데 로딩 안내조차 없었고, 찾고자 하는 검색 결과가 안 나와 여러 번 검색할 수밖에 없었어요.」 / 「게다가 디자이너나 서비스 개발자 없이 만들어졌다보니 구성과 위계 구조가 굉장히 복잡했고, TDS(토스 디자인 시스템)를 사용하지 않아 일관성이 떨어지는 상황이었어요.」
- 출처: [업무용 툴, 내 동료가 정말 만족했나요?](https://toss.tech/article/tablecenter)

### 6.8 업무용 툴의 성과는 줄일 것과 올릴 것으로 나눠 잰다
**규칙**: 업무용 툴의 성과 지표를 줄일 것(작업 시간, 작업 플로우, 비용, 오류, 사용자 요청)과 올릴 것(만족도, 업무 처리량, 사용률, 적용 범위)으로 나눠 세우고 꾸준히 추적한다.
- 왜: 테이블센터 팀은 작업 시간을 줄이면 만족도가 자연스럽게 오를 것이라고 추측하고 검색 시간 단축을 목표로 삼았다. 복잡도가 높은 영향도 기능은 러프한 프로토타입과 소규모·게릴라 UT로 적은 비용에 검증했고, 개선 전후 만족도 설문으로 효과를 비교했다(→ research-ops.md, research-methods.md).
- 근거: 「작업 시간, 작업 플로우, 비용, 오류, 사용자 요청을 줄이거나 ↓」 / 「만족도, 업무 처리량, 사용률, 적용 범위를 올리거나 ↑」 / 「작업 시간을 줄이면 만족도가 자연스럽게 올라갈 거라고 추측했어요.」

### 6.9 사례: 테이블센터 검색어 입력 (Before → After)
- 상황: 데이터 직군이 원하는 테이블을 찾으려고 검색어를 넣는 단계.
- Before: 테이블명에 들어갈 것 같은 단일 키워드만 검색할 수 있었다.
- After: 검색어와 태그를 조합해 원하는 키워드를 조합 검색할 수 있게 했다(예: 'teens'만이 아니라 'teens'+'유스카드').
- 왜 바꿨나: 실제 사용 상황을 관찰하니 검색어 입력 단계에서 헤매는 사람이 많았고, 68.9%가 테이블명에 들어갈 것 같은 키워드를 검색한다고 답했다.

### 6.10 사례: 테이블센터 검색 결과 노출 (Before → After)
- 상황: 검색한 뒤 결과 목록을 보여 주는 방식.
- Before: 검색 결과가 무작위로 노출됐다.
- After: 회사가 중요하게 보는 테이블 태그를 가장 먼저 보이게 하고, 키워드·테이블명·설명 매칭 순과 조회 수·연관도로 우선순위를 매겼다. 사용자가 결과를 직접 좁혀 가도록 모든 열에 필터와 검색 옵션을 넣었다.

- 근거: 「저희 팀은 검색 결과를 보여주는 방식도 검색 시간에 영향을 끼친다는 사실을 알 수 있었어요.」 / 「테이블 검색 경험 만족도는 개선 전 2.71점에서 개선 후 3.88점으로 1.17점 상승했어요.」

## 7. 사장님·B2B 제품

### 7.1 사장님용 제품은 사장님이 스스로 던질 질문으로 만든다
**규칙**: 사장님용 제품은 매출, 꼭 필요한 지출, 정산 후 통장에 들어오는 자금 흐름까지 쉽게 보고 관리하게 하고, 이익과 영업에 직접 도움이 되는 인사이트를 주는 것을 목표로 한다. 기능은 사장님 마인드로 던지는 질문에서 출발한다.
- 왜: 자영업자용 '내 매출 장부' 팀이 이렇게 제품의 목표를 정했다. 집합 금지로 매출이 0이 되어 앱을 켤 이유가 사라졌을 때는 사장님들이 배달로 매출을 찾는 흐름을 따라가, 배달 광고 주소별 수익과 더 매출이 높은 광고 주소 추천을 만들었다(→ problem-solving.md). 같은 시기 매일 보내던 매출 알림을 멈춘 판단은 → principles.md.
- 근거: 「사장님이 장사를 하면서 발생시킨 매출이랑 영업의 꼭 필요한 지출, 매출을 정산한 후 사장님들 통장에 꽂히는 자금의 흐름까지 쉽게 보고 관리하면서 이익과 영업에 직접적인 도움을 줄 수 있는 인사이트를 드리고 있어요」 / 「‘1년 전 오늘, 그땐 얼마를 벌었을까?’ ‘매출은 더 올랐을까?’ ‘그래서 내가 실제로 번 돈은 얼마지?’ 이렇게 사장님 마인드로 고민을 하면서」
- 출처: [오직 한 사람, 사장님을 위하여](https://toss.tech/article/27364)

### 7.2 사례: 포스의 메뉴 추가·등록 (Before → After)
- 상황: 오랫동안 UX가 바뀌지 않은 매장 포스. 사장님들은 불편한 게 없다고 했지만 매장 관찰로 외워야 쓸 수 있는 구조 같은 익숙해진 불편을 찾았다(주문·결제 흐름과 분할 결제는 → domain-flows-and-ia.md).
- Before: 메뉴를 등록하려면 고객센터에 전화하거나 설정 안의 웹 정보에 들어가야 했고, IT에 익숙한 사람이 봐도 어려웠다.
- After: 포스에서 가장 잘 보이는 곳에서 쉽게 등록하게 하고, SNS에 글을 올려 본 사람이면 할 수 있는 난이도로 설계했다. 바쁜 사장님이 글씨를 읽지 않아도 메뉴를 구분하도록 메뉴별 색 구분도 넣었다.
- 왜 바꿨나: 신메뉴를 시도하고 안 팔리는 메뉴를 내리는 일이 잦은데, 메뉴를 만드는 것만으로도 바쁘다. 사장님들은 바빠서 메뉴 글씨를 읽을 시간도 없다.
- 근거: 「근데 신메뉴는 계속 시도도 해야되고 안 팔리는 건 내려야 되고 이게 되게 빈번한데, 메뉴를 만드는 것만으로도 바쁜데, 메뉴 등록하는 건 좀 쉬워야 된다고 저는 생각이 들었거든요.」 / 「사장님들이 바쁘니까 메뉴의 글씨를 읽을 시간도 없다고 하시더라고요.」

### 7.3 사례: 일부 메뉴에만 할인 적용하기 (Before → After)
- 상황: 모닝 할인이 아메리카노에만 적용되는 카페에서, 포스로 주문을 받다가 일부 메뉴에만 할인을 적용하는 순간.
- Before: 할인 적용 버튼을 누르면 주문 리스트가 팝업 안에서 여러 개를 고르는 구성으로 바뀌어 다시 뜨고, 맨 위에 있던 메뉴의 위치가 바뀌었다.
- After: 리스트를 바꾸지 않고, 원래 리스트에서 바로 체크해 할인을 적용한다.
- 왜 바꿨나: 디자이너가 직접 알바를 자처해 오전 주문을 받아 보니, 손님이 줄 선 상황에서 바뀐 구성 속 메뉴를 다시 찾느라 식은땀이 났다. 구성이 바뀌는 것은 그 순간의 알바생에게 곤혹스러운 일이다.
- 근거: 「그리고 그 날은 제가 첫 날 직접 알바를 자처해서 카페에서 오전 주문도 받아봤어요.」 / 「‘구성이 바뀌는 건 이 순간의 알바생에게 곤혹스러운 일이다’ 라는 생각이 들어서 바로 리스트에서 고를 수 있게, 리스트를 변경시키지 않게 하고」

### 7.4 B2B 제품은 며칠 써 본 뒤의 반응까지 확인한다
**규칙**: B2B 제품은 한 번 써 보고 끝나는 제품이 아니므로, 새 방식에 대한 첫 반응이 차가워도 며칠 쓴 뒤 다시 인터뷰해 반응을 확인한다.
- 왜: 포스 필드 테스트에서 3일 뒤 다시 인터뷰하자 반응이 바뀐 것을 확인했다. 필드 테스트에서는 주문 보류(임시저장) 기능 누락과 할인 화면 문제(§7.3)도 발견했다. 사용법을 알려 주지 않고 써 보게 하는 방법과 정답은 필드에 있다는 현장 조사 원칙, 사장님을 만나기 어려운 B2B 제품에서 제품을 잘 모르는 팀원으로 내부 UT를 하거나 리서처가 직접 사업자가 되어 보는 방법은 → research-ops.md, research-methods.md.
- 근거: 「그리고 나서 3일 뒤에 다시 인터뷰를 하면 반응이 바뀌는 걸 확인할 수 있었어요.」 / 「그리고 또 느낀 것은 B2B 제품은 한 번 써 보고 끝이 아니라는 것.」

### 7.5 사례: 결제 단말기의 카드 리더기 고장 (문제 → 해결)
- 문제: 오프라인 결제 단말기 1세대는 카드 리더기가 본체 일체형이라 고장 나면 기기 전체를 수리해야 했다. 수리에 평균 일주일 넘게 걸려 그동안 매장 운영이 멈추거나, 대리점이 늘 여분 기기를 갖고 있어야 해 재고 부담이 컸다.
- 원인: 1세대 출시 후 현장 관찰에서, 사장님이 리더기를 직접 고칠 수 없고 빼기도 어려운 구조가 문제로 드러났다(NFC 위치 문제는 → problem-solving.md).
- 해결: 누구나 쉽게 교체할 수 있는 구조로 바꾸되, 제조 편의 중심인 기존 교체형 단말기와 달리 구조물이 드러나지 않는 하나의 완성된 제품처럼 보이게 하는 것을 목표로 했다. 제조 관점에서는 까다롭지만 누구나 익숙한 C타입 단자를 골랐다. 사용성·심미성·기능성 중 하나를 포기하는 답 대신 질문 자체를 바꾸고 구조를 다시 설계했으며, 기술적으로 되는 답이 아니라 사용자에게 맞는 답을 찾을 때까지 질문해야 한다고 결론짓는다.
- 근거: 「수리에는 평균 일주일 이상이 걸려서, 매장 입장에서는 운영을 멈춰야 하는 큰 부담이 있었죠.」 / 「교체형 단말기들은 전반적으로 사용자 경험보다는 제조 편의에 초점이 맞춰진 디자인이 많았어요.」
- 출처: [하마터면 못생겨질 뻔했다 - 토스 프론트 2 제작기](https://toss.tech/article/toss_front)

### 7.6 사례: 광고주가 직접 쓰는 B2B 광고 플랫폼 (문제 → 해결)
- 문제: 사용자가 지금 필요한 순간에 맞는 광고를 보게 하려면 다양한 광고와 많은 광고주가 필요했지만, 임시로 만든 내부 어드민으로 직접 영업·집행하고 있어 광고를 늘리기 어려웠다. 광고주가 광고를 효율적으로 운영하도록 돕는 B2B 애즈 플랫폼은 ML 로직이 많은 중요한 시스템이었지만 사용성이 전혀 고려되지 않아 너무 복잡했다.
- 해결: 광고주가 직접 집행하는 B2B 광고 플랫폼을 만들고, 모든 사용자에게 알맞은 광고가 잘 배정되게 하는 기능을 많이 만들었다. 복잡한 시스템을 UX로 풀어내는 것을 핵심 과제로 삼았다.
- 결과: 광고 수가 기하급수적으로 늘고 필요한 광고가 적절히 노출됐으며 광고 클릭률도 점점 높아졌다. 1,000명 이상의 광고주가 쓰는 플랫폼이 되었고 다른 팀에서도 벤치마킹했다.
- 근거: 「당시 토스에선 임시로 만든 내부 어드민으로 직접 광고를 영업하고 집행했기 때문에 광고를 크게 늘리기가 어려웠거든요.」 / 「1,000명 이상의 광고주가 활용하는 플랫폼이 됐고, 다른 팀에서도 벤치마킹할 정도였어요.」
- 출처: [토스에서 가장 안 좋은 경험 만들기](https://toss.tech/article/42221), [토스 피플 : 새로운 길을 만들 땐 내 선택을 믿는다](https://toss.tech/article/tosspeople_hyunjung)

### 7.7 사례: 보험설계사용 앱 (문제 → 해결)
- 문제: 설계사가 모바일로 기존 고객의 보험 정보를 볼 수 있으면 쓸 것이라는 가설로 1주 만에 설계사용 앱을 출시했지만 반응이 조용했다.
- 원인: 고객 정보를 볼 수 있다는 것만으로는 설계사가 모이지 않았다. 설계사들은 도움이 필요한 고객을 어디서 만날지 몰라 연락되는 지인 위주로 영업하거나 고객 DB를 사서 권유해 왔다.
- 해결: 테스터 설계사 150명을 모아 토스에서 보험 상담이 필요한 사용자와 매칭해 줬다. 앱에서 무료로 신규 고객을 만날 수 있다는 점이 설계사에게 신선한 충격이 되어 입소문이 났다.
- 근거: 「모바일로 고객 정보를 볼 수 있다는 것만으로는 설계사가 모이지 않았었어요」 / 「사실 설계사분들도 어디서 도움이 필요한 고객을 만날 수 있는지 모르기 때문에 도움이 필요한 고객보다는 연락이 되는 고객 위주로 영업을 해왔었죠」
- 출처: [보험이 필요할 때 어떻게 하세요?](https://toss.tech/article/27342)

## 8. 슬랙봇과 업무 메신저 안의 도구

### 8.1 사례: 이슈봇으로 Jira 이슈 다루기 (Before → After)
- 상황: 슬랙으로 제보받은 이슈를 Jira에 만들고 관리하는 업무 흐름. 토스팀은 좋은 슬랙봇을 채팅 앱에서 업무를 가장 빠르게 처리하도록 돕는 봇으로 정의한다(→ principles.md).
- Before: 「슬랙으로 이슈를 제보받으면, 브라우저를 열고 지라에 접속해서 이슈 생성」
- After: 「이슈봇을 통해 언제 어디서나 슬랙 내에서 즉시 이슈 생성 / 수정 / 완료」
- 왜 바꿨나: 업무 대화가 오가는 슬랙 안에서 다른 페이지로 옮겨 가지 않고 바로 처리하게 해 이슈를 만들고 업데이트하는 시간을 줄였다.
- 근거: 「이슈봇을 통해서 각 이슈를 생성하는 시간을 45초, 업데이트 하는 시간을 15초 절약했는데요.」 / 「2021년에 계산한 바로는 이슈봇이 토스팀원의 업무시간을 1,076시간 절약했는데, 지금까지는 더 많은 시간이 절약됐겠죠.」
- 출처: [슬랙봇 디자인 101](https://toss.tech/article/22439)

### 8.2 플랫폼 위에서 디자인할 때는 구현 제약부터 이해한다
**규칙**: 슬랙 같은 플랫폼 위에서 디자인할 때는 먼저 그 플랫폼의 특이한 구현 제약을 이해한다. 슬랙의 경우 블록킷으로만 UI를 구성하고, 블록 개수와 버튼 글자 수에 제한이 있으며, 링크 텍스트로 페이지를 전환할 수 없다.
- 왜: 슬랙 위 디자인은 디자인 툴에서 그림을 그리는 멘탈 모델과 달라, 시안을 그대로 가져가면 문제가 생기는 경우가 많았다. 제약을 알아야 더 고도화된 UX를 만들 수 있다. (제약 안에서 엔지니어와 대안을 정하는 방식은 → working-with-teams.md, 이미 잘 돌아가는 봇을 레퍼런스로 보는 법은 → research-ops.md)
- 근거: 「먼저, 플랫폼의 특이한 구현 제약사항을 이해해야 해요.」 / 「슬랙 위에서 디자인하는 건 디자인 툴 위에서 그림을 그리는 우리 멘탈 모델과 달라서 시안을 가져가면 문제가 생기는 경우가 많았어요.」
- 출처: [슬랙봇 디자인 101](https://toss.tech/article/22439)

### 8.3 봇은 용도와 업무 맥락에 따라 컨셉을 정한다
**규칙**: 봇이 단순 열람용인지 아닌지 같은 용도와 업무 맥락을 먼저 구분하고, 그에 따라 가독성 위주로 만들지 버튼과 화면 전환 같은 인터랙션을 많이 넣을지 전체 컨셉을 정한다.
- 왜: 토스팀이 사내 업무용 슬랙봇을 많이 만들며 정리한 기준이다. 봇은 단순하고 심플해야 빠르게 태스크를 수행한다는 관찰과 함께 쓰인다(→ principles.md).
- 근거: 「봇은 용도와 맥락에 따라 디자인되어야 해요.」 / 「이런 구분자에 따라 가독성만 따지면 될지, 버튼과 화면 전환 등 인터랙션이 많이 들어가게 만들어야 할지 등 전반적인 컨셉을 정하게 돼요.」
- 출처: [슬랙봇 디자인 101](https://toss.tech/article/22439)

### 8.4 단순한 설정은 봇 안에서, 복잡한 설정은 웹으로 뺀다
**규칙**: 구독이나 ON/OFF 같은 단순한 설정은 봇 안에서 하게 하고, 그보다 복잡한 봇 설정은 자유도가 높은 웹페이지에서 하게 한다.
- 왜: 복잡한 슬랙봇 설정은 슬랙 안에서 하게 하기보다 웹으로 빼는 편이 사용자에게 편리하다는 것을 배웠다.
- 근거: 「복잡한 슬랙봇 설정은 슬랙에서 세팅하게 만드는 것 보다 웹으로 빼는 게 사용자에게 편리하다는 배움이 있었거든요.」 / 「구독이나 ON, OFF를 설정하는 단순한 세팅은 봇에서 설정하도록 하지만 그것보다 복잡한건 웹페이지 안에서 설정하도록 했어요.」
- 출처: [슬랙봇 디자인 101](https://toss.tech/article/22439)

### 8.5 사례: 리서치봇 메시지의 버튼과 설명 (Before → After)
- 상황: 리서치봇 메시지 화면을 디자인 챕터의 주간 PP(Product Principle) 리뷰에서 피드백받아 고친 사례(PP 리뷰와 UT로 점검하는 방식은 → design-systems-and-standards.md).
- Before: 버튼과 설명이 너무 멀리 떨어져 있고 요소가 많았다.
- After: 설명을 아예 버튼 라벨 안에 넣어, 라벨이 조금 길어지더라도 바로 알아보게 했다. PP 리뷰 자리에서 블록킷 빌더로 바로 고쳤다.
- 왜 바꿨나: 리뷰 피드백을 반영했고, 바로 사용자에게 물었을 때 더 잘 이해된다는 답을 들었다. 너무 많은 버튼이나 설명과 버튼이 떨어진 복잡한 인터페이스는 사용자를 헷갈리게 한다(→ principles.md).
- 근거: 「그래서 아예 버튼에 설명을 넣어서 버튼의 라벨 길이가 조금 길더라도 직관적으로 인지하도록 수정했어요.」 / 「그리고 바로 사용자분들께 피드백을 들었을 때 더 잘 이해된다고 이야기해주셨어요.」
- 출처: [슬랙봇 디자인 101](https://toss.tech/article/22439)

### 8.6 설명적인 라벨은 커스텀 이모지로 알아보기 쉽게 한다
**규칙**: 설명적이고 복잡한 라벨을 쉽게 알아보게 하거나 플랫폼이 주는 것보다 UI 구성을 다양하게 하고 싶을 때, 워크스페이스에 커스텀 이모지를 추가해 쓴다.
- 왜: 블록킷이 주는 구성 옵션만으로는 직관적인 봇을 만들기에 부족할 때 이모지로 선택지를 넓혔다. (사내 봇의 말투와 캐릭터는 → interaction.md)
- 근거: 「직관적인 봇을 만들때 설명적이고 복잡한 라벨을 인지가 쉽게 만들거나 UI를 더 잘 구성하는 방법은 슬랙 이모지를 추가하는 것이기도 해요.」 / 「저는 저희 슬랙 워크스페이스에 이모지를 추가해서 UI 구성의 옵션을 블록킷에서 제공하는 것보다 더 다채롭게 구성하기도 했답니다.」
- 출처: [슬랙봇 디자인 101](https://toss.tech/article/22439)

### 8.7 슬랙봇을 만들기 전과 후에 점검한다
**규칙**: 만들기 전에는 슬랙 블록을 이해해 내 언어로 정리하고, 블록킷 빌더를 써 보고, 다양한 봇을 조사한다. 인터페이스를 설계한 뒤에는 고객이나 팀원을 대상으로 UT를 하고, 사용자 맥락을 이해하고 디자인했는지 한 번 더 점검한다.
- 왜: 내부 제품은 사용자를 만나기 쉬우므로 바로 찾아가 사용성 테스트를 할 수 있다(→ design-systems-and-standards.md).
- 근거: 「슬랙 블록에 대해 이해하고 배운점 내 언어로 정리하기」 / 「인터페이스 설계하고나면 고객이나 팀원 대상으로 UT 해보기」 / 「사용자 맥락을 이해하고 디자인했는지 한 번 더 점검하기」
- 출처: [슬랙봇 디자인 101](https://toss.tech/article/22439)

### 8.8 사례: 반영만 하면 되는 요청에 드는 비용과 오토메이션 (문제 → 해결)
- 문제: 슬랙 메시지 전달 기능을 백엔드 제품으로 만든 뒤에도(§5.6), 요청자는 팀 채널에 찾아와 키워드·액션 정보를 말해야 했고 팀은 이를 정리해 다른 작업과 우선순위를 비교한 뒤 개발해야 했다.
- 원인: 어렵지 않고 요청대로 반영만 하면 되는 일인데도 요청·정리·우선순위 비교·개발에 드는 비용이 컸다.
- 해결: 사용자가 직접 설정할 수 있게 UI를 주는 '오토메이션' 제품을 만들었다. 프론트 없는 백엔드 MVP로 가치를 확인한 뒤 최소 기능으로 시작했고, 사용자가 할 일의 목적을 정해 두지 않고 수단만 제공했다(제품화 판단과 최소 기능 범위는 → decision-making.md, 수단만 제공하는 원칙은 → principles.md).
- 결과: 1년 사이 700명 정도가 3,000개 정도의 오토메이션을 직접 만들었다.
- 근거: 「이게 사실 그렇게 어려운 요청이 아니고 요청대로 반영만 하면 되는 거였지만 이런 비용들이 너무 크게 느껴져서 아깝다는 생각을 했어요」 / 「그래서 사용자가 직접 이것들을 할 수 있도록 UI를 제공할 수 있게 오토메이션이라는 이름의 제품을 만들면 어떨까 생각을 했죠.」
- 출처: [3,250개의 요구사항을 해결한 1개의 제품](https://toss.tech/article/27398)

### 8.9 사례: 추천 템플릿을 보여 주는 방법 (Before → After)
- 상황: 오토메이션 사용자에게 좋은 사용 예시(템플릿)를 추천하려던 상황. 메이커가 출시 전에 갖추고 싶던 기능(권한, 템플릿, 팀별 폴더 등)은 출시 후 사용 모습을 보며 대응하기로 했다(→ decision-making.md).
- Before: 템플릿을 보여 주는 별도 기능이 있으면 좋겠다고 생각했다.
- After: 오토메이션 제목에 '템플릿'이라는 머릿말을 다는 것으로 충분했다.
- 왜 바꿨나: 예상과 달리 템플릿을 쓰는 사용자보다, 실제로 동작하는 오토메이션을 보고 찾아와 복제해 쓰는 사용자가 훨씬 많았다.
- 근거: 「아까 말했던 템플릿 같은 경우에 이제 오토메이션 제목에 템플릿이라는 머릿말을 다는 것으로도 충분했었고,」 / 「예상하지는 못했는데 그렇게 템플릿을 사용하시는 유저들보다 실제 동작하는 오토메이션을 보고 찾아오시는 분들이 훨씬 많았어요.」
- 출처: [3,250개의 요구사항을 해결한 1개의 제품](https://toss.tech/article/27398)

### 8.10 사례: 메시지 속 설정 링크가 복제 경로가 되다 (문제 → 해결)
- 문제: 오토메이션을 만든 사람들이 쓰면서 조금씩 고치고 싶어 했다.
- 해결: 오토메이션이 보내는 액션 메시지에 오토메이션 설정으로 바로 가는 링크를 넣었다.
- 결과: 다른 사람들이 그 링크를 타고 들어와 설정을 구경하고 복제해 썼다. 예를 들어 로고 리소스 링크를 안내하는 브랜드 디자인팀의 오토메이션이 비슷한 문의를 받던 여러 팀으로 복제됐다.
- 근거: 「이걸 쓰시면서 조금씩 수정하고 싶어하시기 때문에 액션하는 메시지에다가 오토메이션 설정으로 바로 갈 수 있는 링크를 넣었어요.」 / 「그런데 이 링크를 오히려 다른 분들이 타고 설정 어떻게 했나 구경하시는 거예요.」
- 출처: [3,250개의 요구사항을 해결한 1개의 제품](https://toss.tech/article/27398)

### 8.11 사례: 설정 화면에서 바로 복제하기 (Before → After)
- 상황: §8.10의 바로가기 링크로 오토메이션 설정 화면에 들어온 사용자가 그 오토메이션을 복제하려는 상황.
- Before: 복제 기능이 목록에만 있어, 설정 화면에서 뒤로가기로 목록에 나가 이름을 다시 확인하고 복제해야 했다.
- After: 설정 화면에도 복제 기능을 추가했다.
- 왜 바꿨나: 사용자가 실제로 쓰는 모습을 보며 이 불편을 발견했다. 사용자가 링크를 타고 설정 화면으로 들어온다는 실제 경로에 맞춰 기능을 더했다.
- 근거: 「그런데 그러면 뒤로가기를 눌러서 목록으로 나가야되는 거예요.」 / 「이런 불편함을 사용자분들이 사용하시는 것을 보면서 ‘아, 이건 설정 화면에 복제할 수 있는 기능이 있어야겠구나’라고 생각을 해서 이렇게 추가를 하게 된 경우도 있었죠.」
- 출처: [3,250개의 요구사항을 해결한 1개의 제품](https://toss.tech/article/27398)

### 8.12 사례: 업무 흐름 밖에 있던 AI 봇 (문제 → 해결)
- 문제: 디자이너가 사용성을 더 자주 점검하도록 토스 사용자처럼 학습된 AI 봇(휴리봇)을 노코드 챗봇으로 만들어 가치는 검증했다. 하지만 챗봇은 디자이너의 작업 워크플로에 없는 단계라 접근성이 떨어져 자주 쓰이지 않았고, 다른 사람의 대화 이력을 볼 수 없어 봇을 디벨롭하고 관리하기도 어려웠다.
- 해결: 문제 해결과 제품 확장을 위해 내재화를 결정했다. MVP 스펙에서는 있으면 좋은 정도의 기능을 뺐다(→ decision-making.md, AI 봇을 만든 과정은 → ai-practices.md).
- 근거: 「챗봇은 디자이너의 작업 워크플로에 없는 단계이기 때문에 접근성이 떨어졌고, 그렇다 보니 자주 사용하지 않게 되는 문제가 발생했어요.」 / 「또한 다른 사람의 대화 이력을 확인할 수 없기에 제가 봇을 좀 더 디벨롭하거나 관리하는 것도 어려웠고요.」
- 출처: [휴리봇 이야기 #1: 토스는 AI 봇에게 사용자 인터뷰를 한다](https://toss.tech/article/research-platform-ai)

## 9. 메이커를 위한 사내 도구: 디자이너·개발자·비전문가가 쓰는 툴

### 9.1 일하는 방식에 맞는 툴을 직접 만드는 선택지를 둔다
**규칙**: 어떤 툴을 쓰느냐가 일하는 방식과 생산성을 좌우한다는 점을 기준으로, SaaS를 사서 쓰는 대신 일하는 방식에 맞는 툴을 직접 만들어 최적화하는 선택지를 둔다. 고객 데이터를 외부에 맡길 수 없는 환경이라면 더욱 그렇다.
- 왜: 토스는 금융 기업이라 고객 데이터를 외부에 맡길 수 없는 제약이 있는데, 이 환경 덕분에 일하는 방식에 맞게 최적화하고 필요한 기능을 빠르게 구현할 수 있었다. 시중 툴을 먼저 써 보고 꼭 필요한 기능이 안 될 때 만든 사례(오토메이션)와, 시중 도구가 내 맥락을 모른다는 이유로 직접 만든 사례(할 일 관리 도구)는 → decision-making.md, data-and-experiments.md.
- 근거: 「어떤 툴을 쓰느냐는 곧 우리의 일하는 방식과 생산성을 좌우하니까요.」 / 「게다가 토스는 금융 기업이라 고객 데이터를 외부에 맡길 수 없는 환경적인 제약도 있어요.」
- 출처: [AI 시대에 디자이너로 살아남기](https://toss.tech/article/removing_designers_in_ai_era), [3,250개의 요구사항을 해결한 1개의 제품](https://toss.tech/article/27398), [매일 하던 업무를 디자인하기](https://toss.tech/article/todolist)

### 9.2 툴을 옮길 때 기존 툴의 사용 방식을 그대로 옮기지 않는다
**규칙**: 디자인 툴을 바꿀 때 기존 툴에서 쓰던 방식을 그대로 옮기지 않고, 새 툴의 특성에 맞게 가장 효율적으로 쓸 방법을 다시 설계한다.
- 왜: 스케치(드로잉 기반)와 프레이머(코드 기반)는 전혀 다른 툴이어서 같은 방식을 옮기는 것은 의미가 없었다. 플랫폼 디자이너는 메이커의 디자인 작업 과정의 비효율을 무슨 방법을 써서라도 효율화하는 역할이다(→ design-systems-and-standards.md, team-roles-and-growth.md).
- 근거: 「둘은 전혀 다른 툴이기 때문에, 스케치에서 사용하는 방식 그대로 프레이머에 옮기는 것은 큰 의미가 없다고 생각했거든요.」 / 「툴에 특성에 맞게 코드를 활용해서 가장 효율적으로 사용할 수 있는 방법을 적용하고자 했어요.」
- 출처: [플랫폼 디자이너가 효율을 만들어내는 법](https://toss.tech/article/how-platform-designer-make-effectiveness)

### 9.3 사례: 플로우차트 컴포넌트 (Before → After)
- 상황: 복잡한 제품에서 화면 사이의 관계와 흐름을 표현하는 플로우차트 컴포넌트를 새 디자인 툴로 옮기는 작업.
- Before: 필요한 형태의 화살표를 하나씩 옵션으로 추가하는 더하기 방식이었다. 새 툴에는 반전 기능과 단계별 드롭다운이 없어 관리할 가짓수가 늘고 모든 화살표를 한 번에 보며 골라야 했으며, 방향만 바꾸고 싶어도 다른 화살표를 찾아야 했다.
- After: 화살표를 돌리거나 뒤집었을 때 공통으로 겹치는 가장 기초적인 형태를 찾아 정의하고, 방향·레이블·선 스타일 같은 옵션을 조합하는 곱하기 방식의 단일 컴포넌트로 만들었다.
- 왜 바꿨나: 위아래만 바뀐 화살표를 쓰려고 다른 화살표를 찾아야 하는 것은 상식적이지 않았다. 곱하기 방식이라 계속 확장할 수 있었고, 디자이너뿐 아니라 PO도 복잡한 제품의 구조도를 그릴 수 있게 됐다.
- 근거: 「그냥 위아래가 바뀐 화살표를 쓰고 싶었을 뿐인데 왜 다른 화살표를 써야 할까? 의문이 들었죠. 우리가 좀 더 상식적으로 플로우차트를 쓰기 위해서는 더하기 방식이 아닌 곱하기 방식을 써야 했어요.」 / 「곱하기 방식을 사용했기 때문에 지속적인 확장이 가능했죠.」
- 출처: [플랫폼 디자이너가 효율을 만들어내는 법](https://toss.tech/article/how-platform-designer-make-effectiveness)

### 9.4 사례: 곱하기 방식 옵션의 예상치 못한 동작 (문제 → 해결)
- 문제: 하나씩 그리는 방식이 아니어서 옵션 조합이 예상치 못하게 동작했다. 화살표는 이미지라 어떤 조작에도 문제가 없었지만, 텍스트가 들어가는 레이블은 반전되거나 회전되면 안 됐다.
- 해결: 반전은 화살표를 반전시킨 뒤 텍스트박스를 다시 반전시켜 해결했다. 회전과 반전을 함께 할 때 레이블 위치가 예상과 다르게 움직이는 문제는 정확한 레이블 위치를 찾는 규칙을 만들어 해결했다.
- 근거: 「하지만 곱하기 방식으로 옵션을 만들어 낸다는 것이 쉽지만은 않았어요. 하나씩 그리는 더하기 방식이 아니다 보니, 예상치 못하게 동작하는 모습이 나오기도 했기 때문이에요.」 / 「레이블에는 텍스트가 들어가기 때문에 텍스트는 반전도, 회전도 하면 안 됐어요.」
- 출처: [플랫폼 디자이너가 효율을 만들어내는 법](https://toss.tech/article/how-platform-designer-make-effectiveness)

### 9.5 내부 도구라도 보기 좋은 결과물을 포기하지 않는다
**규칙**: 쉽게 만드는 방식이 보기 불편한 결과물을 낳는다면, 내부 도구라도 심미적으로 좋은 결과물을 위해 문제를 풀어 간다.
- 왜: 코드를 단순하게 짜면 쉽게 만들 수 있었지만 보기 불편한 플로우차트가 될 수밖에 없었고, 디자이너는 그런 플로우차트로 화면을 그리는 것을 받아들일 수 없어 §9.4 같은 문제를 하나씩 풀었다.
- 근거: 「코드를 단순하게 짜면, 쉽게 만들 수 있지만, 모서리가 뾰족하게 각져있는 형태의 보기 불편한 플로우차트를 그릴 수밖에 없었어요.」 / 「하지만 저는 이런 플로우차트로 화면을 그린다는 건 참을 수가 없었고, 심미적으로 아름다운 플로우차트를 그리기 위해서 아래와 같은 문제를 해결해 나갔어요.」
- 출처: [플랫폼 디자이너가 효율을 만들어내는 법](https://toss.tech/article/how-platform-designer-make-effectiveness)

### 9.6 사례: 개발자가 코드에서 에러 메시지를 쓰는 과정 (Before → After)
- 상황: 좋은 에러 메시지 기준을 만들어도 팀이 따르지 않으면 의미가 없어서, 기준을 작업 환경 안에서 바로 쓰게 만든 사례(에러 메시지 기준과 템플릿 자체는 → ux-writing-errors-marketing.md).
- Before: 개발자가 디자이너에게 문구를 묻고, 맥락을 모르는 디자이너는 PO나 서버 개발자에게 설명을 들은 뒤 문구를 써서 iOS·안드로이드·서버 개발자에게 다시 전달했다. 번거로워서 디자이너와 논의 없이 직접 쓰거나 다른 제품 문구를 복사하는 경우가 많았다.
- After: 코드를 쓰면서 에러 메시지 컴포넌트를 불러오는 에러 메시지 라이브러리를 만들어 한 줄이면 되게 했다. 커뮤니케이션이 줄었고, 논의하더라도 템플릿이라는 기본값에서 시작한다.
- 왜 바꿨나: 비슷한 에러끼리 같은 문구로 규격화되어 검색이 쉬워지고 제품의 일관성도 좋아진다.
- 근거: 「그런데 에러 메시지 라이브러리가 생기고부터는 개발자가 디자이너와 커뮤니케이션할 일도 줄어들고, 하더라도 템플릿이라는 기본값에서 논의가 시작되니 금방 끝낼 수 있게 됐죠.」 / 「비슷한 에러끼리는 똑같은 문구로 규격화되어있으니 검색하기도 쉬워지고, 제품에 일관성을 부여하기도 좋아졌고요.」
- 출처: [가이드라인을 시스템으로 만드는 법](https://toss.tech/article/introducing-toss-error-message-system)

### 9.7 사례: 디자이너가 디자인 툴에서 문구를 넣는 과정 (Before → After)
- 상황: 디자이너가 프레이머에서 화면에 에러 문구를 넣는 과정.
- Before: 템플릿이 노션·스프레드시트 등 디자인 툴 밖에 있어 매번 화면 밖으로 나갔다 돌아와야 했고, 검색이 어려웠으며, 타이틀과 디스크립션을 따로 복사해 컴포넌트에 붙여 넣어야 했다. 컴포넌트에는 더미 텍스트가 들어 있었다.
- After: 프레이머 안에서 문구를 검색해, 자주 쓰는 문구가 들어간 컴포넌트를 프리셋으로 통째로 붙여 넣는 프레이머링을 만들었다. 컴포넌트를 불러오면 그 컴포넌트에서 자주 쓰이는 문구 템플릿을 미리 볼 수 있다.
- 왜 바꿨나: 메시지를 작업 환경 위에서 바로 검색할 수 있게 해 접근성 문제를 풀려고.
- 근거: 「왜냐하면 템플릿이 노션이나 스프레드 시트 등 디자인 툴 밖에 있었기 때문에, 문구를 쓸 때마다 디자인 화면 밖으로 나갔다가 다시 돌아와야 했기 때문이에요.」 / 「이런 접근성 문제를 해결하기 위해, 메시지를 작업 환경 위에서 바로 검색할 수 있으면 좋겠다는 생각이 들었어요.」
- 출처: [가이드라인을 시스템으로 만드는 법](https://toss.tech/article/introducing-toss-error-message-system)

### 9.8 메이커가 작업 도구 밖으로 나가지 않게 한다
**규칙**: 메이커가 자주 찾는 자원(그래픽 자산, 특수문자, 문구 템플릿)은 작업하는 도구 안에서 바로 찾고 넣을 수 있게 만든다.
- 왜: 디자인플랫폼팀은 그래픽 컴포넌트를 그래픽 자산 관리 플랫폼과 연결하고 자산에 태그를 붙여, 디자이너가 떠오르는 단어로 원하는 그래픽을 고르게 했다. 전용 서체를 만들 때는 서체를 가장 많이 쓸 프로덕트 디자이너가 일러스트레이터를 켤 일이 없어 글리프 창으로 특수문자를 넣기 어렵다는 점을 보고, 프레이머에 마크다운 룰을 만들어 텍스트만으로 모든 특수문자를 불러오게 했다. 문구 템플릿을 툴 안으로 들인 사례는 §9.7.
- 근거: 「디자이너는 툴 밖을 벗어나지 않고 원하는 그래픽을 고를 수 있게 되었습니다」 / 「이 서체를 디자이너분들이 제일 많이 쓸 텐데 프로덕트 디자이너분들은 일러스트레이터를 켤 일이 아예 없잖아요」
- 출처: [지금, 툴이 아닌 틀을 바꿔야 할 때](https://toss.tech/article/27344), [모두를 위한 단 하나의 서체](https://toss.tech/article/27358)

### 9.9 공유 자산은 실제 제품과 같은 링크로 연결해 늘 최신으로 둔다
**규칙**: 그래픽 같은 공유 자산은 누구나 내려받을 수 있는 한곳에 모으되, 따로 운영하는 사본이 아니라 실제 제품에 쓰이는 자산과 같은 링크로 연결해 별도 관리 없이도 늘 최신이 되게 한다.
- 왜: 만든 그래픽은 실제 제품에 쓰여야 의미가 있다. 리소스센터는 제품 그래픽과 같은 링크로 연결되어 있어, 제품 그래픽을 바꾸려면 리소스센터 그래픽을 바꿔야 한다.
- 근거: 「그런데 저희가 만든 모든 그래픽들이 사실 실질적으로 쓰이지 않으면 아무 의미가 없겠죠 제품에 잘 쓰이는 게 가장 중요하니까요」 / 「리소스센터의 핵심은 별도로 운영되는 홈페이지가 아니라, 실제 토스 제품에 적용되는 그래픽이랑 동일한 링크로 연결되어 있다는 점이에요」
- 출처: [그래픽, 보이는 아름다움 그 너머](https://toss.tech/article/27360)

### 9.10 비전문가가 쓰는 사내 AI 도구는 입력을 줄이고 전문 설정은 뒷단에 둔다
**규칙**: 사내 도구의 사용자가 그 분야의 전문 지식이 없다면 필수 입력을 최소로 줄이고, 결과 품질을 좌우하는 세부 설정은 그 분야 전문가가 뒷단에 붙여 두고 계속 개선한다.
- 왜: 협업할 팀원은 100명이 넘는데 그래픽 디자이너는 5명뿐이어서, 토스의 그래픽 톤을 이해하는 AI 그래픽 생성기 토스트를 사내 서비스로 만들었다. 사용자가 생성 AI나 그래픽 디자인 지식이 없으므로 필수 입력을 그래픽 타입 선택과 개체 입력 두 가지로 줄였고, 타입별로 일정한 톤이 나오게 하는 프롬프트 설정은 그래픽 디자이너가 맡았다(→ ai-practices.md).
- 근거: 「하지만 토스트의 사용자는 생성 AI나 그래픽 디자인에는 전문 지식이 없는 사람들이기 때문에 배경지식 없이도 쉽게 이용할 수 있게 했어요.」 / 「디테일한 부분을 연구하고, 일정한 톤으로 나오도록 설정값 만드는 일은 이 분야의 전문가인 그래픽 디자이너의 역할이라고 생각한 거죠.」
- 출처: [토스의 AI 그래픽 생성기, 토스트를 소개합니다 #1](https://toss.tech/article/ai-graphic-generator-1)

### 9.11 사례: 수만 개 화면 중 참고할 화면 찾기 (문제 → 해결)
- 문제: 수백 개 제품, 수만 개 화면 중에서 참고할 화면을 찾기 어려웠다. 인터뷰한 디자이너 모두 화면 찾기를 힘들어했다.
- 원인: 화면을 만든 디자이너를 수소문해 디자인 파일을 받아야 해서, 클라우드의 파일을 잇는 매개체가 사람이었다.
- 해결: 디자이너가 만드는 모든 화면을 검색할 수 있으면 이 비효율이 사라진다는 가설로, 스콥을 극단적으로 줄여 개발자 없이 노코드 툴로 하루 만에 화면 검색 제품(토스파)을 만들었다. 설문으로 기준 데이터를 만들어 목표 지표를 정한 뒤 배포했다(→ data-and-experiments.md).
- 결과: 높은 사용량과 만족도를 얻었다. 배포 후 디자이너들이 화면을 쇼핑하듯 스크롤하며 본다는 새 사용 패턴도 발견했다(→ research-ops.md).
- 근거: 「클라우드의 파일을 이어주는 매개체가 아이러니하게도 사람이었어요.」 / 「그래서 디자이너가 만드는 모든 화면을 검색할 수 있으면 이 비효율은 없어진다고 생각했어요.」
- 출처: [토스에서 하루 만에 제품 출시하는 법](https://toss.tech/article/launching-product-in-one-day)

## 10. 점검 질문
- 이 툴이 동료가 더 정확하고 빠르게 일하게 돕는가, 내부 툴의 비효율이 최종 고객의 대기 시간·만족도·사업 시작 시점으로 옮겨 가고 있지 않은가? (§1.1, §1.2)
- 어드민 작업에 디자이너가 처음부터 참여하는가, 일이 넘칠 때 어떻게 일할지부터 정의했는가? (§1.3, §1.4)
- 보이지 않는 내부 업무와 내부 효율화 제품도 같은 기준으로 고민했는가? (§1.5)
- 사용자 수가 적다는 이유만으로 리소스 대비 임팩트가 큰 내부 제품을 버리고 있지 않은가? (§1.6, §1.7)
- 설계 전에 사용자가 어떤 순서와 방식으로 일하는지 관찰했는가, 업무 메모와 실제 작업 장면까지 봤는가? (§2.1)
- 제품 구조가 사용자가 문의를 좁혀 가는 실제 패턴을 따르고, 대상의 상태에 따라 가장 먼저 필요한 정보로 바로 보내는가? (§2.2, §2.3)
- 입력창이 다른 창에 가려지지 않는가, 정보를 확인하는 순서와 입력칸 순서가 같은가? (§2.4, §2.5)
- 기존 업무 흐름에서 꼭 남길 단계만 남기고, 제품이 이미 아는 정보와 중복 입력을 자동으로 채우는가? (§3.1, §3.2)
- 완전 자동화가 어렵다면 가능한 작은 부분부터 자동화했는가? (§3.3, §3.4)
- 처리 알림이 사용자가 가장 많이 쓰는 곳으로 가는가, 반복되는 승인 클릭까지 연동으로 없앨 수 있는가? (§3.5, §3.6)
- 문제가 너무 많아 보일 때 하나의 원인과 궁극적인 목적으로 압축해 봤는가? (§4.1)
- 숙련도와 상관없이 놓치는 것 없이 한 방향으로 끝낼 수 있게 제품이 업무를 이끄는가? (§4.2)
- 기다리는 일을 사람이 들락날락하며 확인하지 않고, 제품이 상태별로 관리하고 할 일을 업무 화면 안에서 만들어 주는가? (§4.3, §4.4)
- 자동화 전에 업무 방식을 통일해 결과를 유형화했는가, 통 텍스트 템플릿 대신 조각난 문구를 골라 채우게 했는가? (§4.5, §4.6)
- 제각각 보이는 계약·요청·기능에서 공통 규칙과 반복 패턴을 찾았는가, 팀별 차이는 옵션으로 뺐는가? (§5.1, §5.2, §5.3, §5.6)
- 패턴 시스템이 만드는 사람의 개발 부담과 쓰는 사람의 학습 부담을 함께 줄이는가? (§5.4)
- 같은 기능을 제품·계열사마다 바닥부터 만들고 있지 않은가, 플랫폼으로 공유할 수 있는가? (§5.5)
- 권한처럼 처음 정의하는 구조의 러닝을 팀 전체가 공유하고 있는가? (§5.7)
- 매일 쓰는 업무 도구를 한꺼번에 바꾸려 하지 않는가, 작게 쪼개 우선순위대로 배포하고 예전 환경과 함께 쓰는 과도기를 두었는가? (§6.1, §6.5)
- 포기하면 안 되는 기존 습관을 파악하고 살렸는가? (§6.2, §6.3)
- 큰 변화는 충분히 미리, 여러 번 알리고 사소한 공지는 줄였는가? (§6.4)
- 사용자가 신규 제품과 레거시를 오가고 있지 않은가, 실제 업무 과정을 본떠 일원화했는가? (§6.6)
- 업무용 툴의 성과를 줄일 지표와 올릴 지표로 세우고 개선 전후를 비교했는가? (§6.7, §6.8, §6.9, §6.10)
- 사장님이 스스로 던질 질문(얼마 벌었나, 실제로 번 돈은 얼마인가)에 답하는가? (§7.1)
- 바쁜 현장에서 자주 하는 일을 학습 없이 할 수 있고, 조작 도중 목록의 구성이나 항목 위치가 바뀌지 않는가? (§7.2, §7.3)
- B2B 제품의 첫 반응만 보고 판단하지 않고 며칠 뒤 다시 확인했는가? (§7.4)
- 사장님이 직접 교체할 수 있는 구조인가, 복잡한 B2B 시스템을 사용자가 직접 쓸 수 있게 풀었는가, 사용자가 실제로 원하는 가치를 주는가? (§7.5, §7.6, §7.7)
- 사용자가 이미 일하는 메신저 안에서 다른 페이지로 가지 않고 일을 끝낼 수 있는가? (§8.1)
- 플랫폼의 구현 제약을 먼저 이해했는가, 봇의 용도에 맞춰 컨셉을 정하고 복잡한 설정은 웹으로 뺐는가? (§8.2, §8.3, §8.4)
- 설명과 버튼이 떨어져 있지 않은가, 만든 뒤 팀원 대상 UT와 맥락 점검을 했는가? (§8.5, §8.6, §8.7)
- 반영만 하면 되는 반복 요청을 사용자가 직접 설정할 수 있게 했는가, 출시 후 실제 사용 모습과 유입 경로를 보고 기능을 조정했는가? (§8.8, §8.9, §8.10, §8.11)
- 새 도구가 사용자의 작업 워크플로 안에 들어가 있는가? (§8.12)
- 일하는 방식에 맞는 툴을 직접 만드는 선택지를 검토했는가? (§9.1)
- 툴을 옮길 때 기존 사용 방식을 그대로 옮기지 않았는가, 옵션 조합으로 확장할 수 있게 하면서 보기 좋은 결과물도 지켰는가? (§9.2, §9.3, §9.4, §9.5)
- 기준·템플릿·자산을 메이커의 작업 환경 안에서 바로 쓸 수 있고, 실제 제품과 같은 링크로 최신 상태를 유지하는가? (§9.6, §9.7, §9.8, §9.9)
- 비전문가 사용자의 필수 입력을 줄이고 전문 설정은 뒷단에 두었는가? (§9.10)
- 파일과 화면을 사람이 수소문해 이어 주고 있지 않은가? (§9.11)
